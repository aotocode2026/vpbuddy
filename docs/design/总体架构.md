## 〇、口径校准 (v1.20, 2026-06-24)

本架构只服务于一个场景: **我(VP/创业者/产品经理)日常跟各种人开会时，需要能把讨论内容实时沉淀为 6 类结构化物(需求/架构/任务/API/风险/Demo HTML)。沉淀物可以跟同龄人协作讨论，也可以作为下一个会议的上下文。**

### 不是:
- ❌ 不是通用 AI agent 框架
- ❌ 不是会议录播/回放/编解码系统
- ❌ 不是客服聊天机器人
- ❌ 不是企业内部知识管理系统 (但聊天上传可充当)
- ❌ **不是展示项目 / POC / demo** — 是真生产工具

### 用户故事一句话:
> "我开会时开着 VPBuddy 客户端自动收声，会议开始 15 秒后就有 6 类文档 + 1 个 HTML 原型 Demo，我还能跟 AI agent 对话追问细节、调整方向。"

## 二、ASR 架构 (v1.43 重写)

### 百炼 Fun-ASR-Realtime

```
客户端 PCM 帧 (16kHz mono int16)
  └─ WebSocket ─→ GPU 服务器 (fastapi_app.py)
                    └─ dashscope Recognition ─→ 百炼云端 WS
                                               │
                                               ▼
                                          sentence_end callback
                                               │
                    ┌──────────────────────────┘
                    ▼
              BailianCallback.on_event()
              ├─ 推送 transcript JSON 回客户端
              ├─ 写入 MeetingState.cleaned_text (每句追加)
              └─ 回调 on_state_changed → task_manager.submit (事件驱动文档生成)
```

**关键设计**:
1. **单条 WS 连接**: 从 start 到 stop 同一条流，不 restart，模型内部自然利用上文语音特征
2. **句子级写入**: 每句 `sentence_end=True` 时立刻写 `cleaned_text`，文档 agent 实时可见
3. **无外部上下文注入**: dashscope Recognition API 不接受外部 context 参数，也不需要——WS 双工流天然带上下文

**百炼自动重连 (v0.22.8)**: 百炼 WS 长时间无有效语音会关闭 (idle timeout ~10-20s)。`on_close` 回调标记 `needs_reconnect=True`，下次 `send_audio` 时自动调用 `restart_session()` 静默重建 Recognition。客户端 WS 不断，SSE 不推 `recording-disconnected`。

**转写分段持久化 (v0.23.3, ADR-0059)**: 每句转写完成后 `_persist_segment()` 幂等写入 `data/meetings/{mid}.stream.json` 的 `transcript_segments` 数组。分段 id = `{recording_session_id}:{sentence_count}`，噪音/空文本跳过。写入失败不阻塞主流程。

## 三、文档自驱动生成 (v1.51 事件驱动重构)

### v1.51 关键变更 (2026-07-16)

| 变更 | 旧 (v1.45-v1.50) | 新 (v1.51) |
|------|-----------|-----------|
| 文档触发方式 | gkd 后台线程每 6s 轮询 298 个会议的 `cleaned_text` hash | **事件驱动**: bailian_asr 每句转写完成 → `on_state_changed` 回调 → `task_manager.submit` |
| gkd daemon | 扫描全部 meetings (含历史,启动时全量提交) | **仅扫描有活跃 SSE 订阅者的会议**, 已无 SSE 的跳过 |
| gkd 初始触发 | `_gkd_first=True` → 进程重启时所有 298 会议触发一轮 batch_docs | **去掉 `_gkd_first`** — 进程重启不触发历史会议 |
| 状态写入 | `st.exists(mid)=True` 才写 → **新会议 first sentence 丢失** | **`st.exists(mid)=False` → 创建 `MeetingState(meeting_id=mid)`** 再写 |
| WS 断连 | `connection lost` 不触发文档生成, 等用户重连 | **WS 断连也触发 `task_manager.submit`**, 保留 reconnect 能力 |
| task_manager workers | 4 | **8** (避免积压) |
| chat 上传 | 文本入 KB + 图片不入 KB | **全部只落盘 `uploads/{mid}/`，不入 KB** |
| VP Chat prompt | "6 个子 agent" + "调度" | **"2 个自动子 agent (batch_docs + demo)"，系统自动调度** |
| batch_docs prompt | "材料已入 KB" → 误导 agent 搜 Chroma | **`read_file` 读 `uploads/{mid}/` 路径** |

### 事件驱动架构

```python
# fastapi_app.py — ws_realtime_asr 内联回调
def _on_state_changed(_mid: str):
    from ..task_manager import get_task_manager
    from ..sub_session_controller import run_docs
    get_task_manager().submit(_mid, run_docs)

session = start_session(..., on_state_changed=_on_state_changed)
```

```python
# bailian_asr.py — BailianCallback.on_event()
if is_end and text.strip():
    self._write_state(cleaned, ...)       # 先落盘
    if self._on_state_changed is not None:
        self._on_state_changed(mid)       # 再通知
```

**时间线**:
```
T+0s    WebSocket ASR 连接建立
T+2s    第 1 句话转写完成 → on_state_changed → task_manager.submit
        → batch_docs agent (fork 自 chat) → MiniMax-M3 → write_file × 5
        → demo agent (fork 自 chat) → MiniMax-M3 → write_file HTML
T+5s    第 2 句话转写完成 → submit → task_manager 检测 running → defer (排队)
T+20s   batch_docs 完成 → 自动 kick deferred 任务 → demo agent
T+30s   第 n 句话 → submit → 以此类推 (task_manager 内部排队长)
...
WS 断连 → finally 块也触发 submit → 最后一轮文档
会议结束 → POST /close → _close_meeting → 经验蒸馏 + 最终文档
```

**关键设计**:
1. **零轮询**: 不再有 gkd 或 `_kick_docs` 等定时器, 输入到达即触发
2. **task_manager 排队**: `MeetingTaskQueue.submit` 内部 running→defer→kick, 不会堆积重复
3. **无硬性时间约束**: 不设 6s/15s debounce, 句子到就触发, task_manager 负责合并
4. **回调线程安全**: dashscope 回调线程 → `call_soon_threadsafe` 解耦,`on_state_changed` 在 WS async 上下文执行

### gkd 守护线程 (退化角色)

gkd 现在只做**兜底**: 扫描有活跃 SSE 订阅的会议, hash 变化时提交。主要文档生成由 `on_state_changed` 事件驱动。

```python
# fastapi_app.py — gkd daemon
def _gkd_loop():
    while True:
        sleep(6)
        with _gkd_subs_lock:
            active_mids = [m for m, subs in _gkd_subs.items() if subs]  # 只有活人
        for mid in active_mids:
            if hash_changed:
                _tm.submit(mid, _run_docs)
```

### _write_state 自动创建 MeetingState

```python
# bailian_asr.py
if st.exists(mid):
    state = st.load(mid)
else:
    state = MeetingState(meeting_id=mid)  # v0.23.1: 首次见面自动创建
state.cleaned_text = ...
st.save(state)
```

### SSE 生命周期 (v1.44 新增)

客户端使用 **双 flag** 解耦音频采集与事件流:

| flag | 控制范围 | 设 true | 设 false |
|------|---------|---------|----------|
| `capturing` | 音频采集 + WS 发送 | `start_realtime_capture` | 用户点"停止采集"或音频设备初始化失败 |
| `sse_active` | SSE 事件流 (独立) | `start_realtime_capture` (与 capturing 同时) | `run_realtime_loop` 在 `POST /close` 后 **等 30 秒** |

**关键设计原则**:
- 停采集 ≠ 停会议 — `stop_capture` 只设 `capturing=false`, 不碰 `sse_active`
- WS `send_frame()` 失败只 `break` 发送循环, 不设任何 flag
- SSE 在 close 后额外保持 30 秒, 确保接收 `demo-new-version`、`doc-update` 等异步生成的事件
- GPT 4-5-10 之前 `capturing` 一拖三 (cpal/WS/SSE) 导致 "WS 断连→杀 SSE→demo 送达失败"

## 四、session 架构 (v1.51, ADR-0041)

```
master session: meeting:{mid}:vp-chat     ← 客户端 Chat 页签 (系统自动调度, VP 不需要手动触发)
   ├── fork → meeting:{mid}:batch_docs    ← 继承 chat 历史, 1 次 LLM 调用生成 5 文档 (req/arch/tasks/api/risk)
   └── fork → meeting:{mid}:demo          ← 继承 chat 历史, 生成 demo HTML
```

**VP Chat prompt (v0.23.1)**: system prompt 已从 "6 个子 agent" 纠正为 "2 个自动子 agent"，明确告知 agent 子 agent 由系统自动调度（每句转写完成即触发），agent 只需专注回答 VP 问题，不需手动触发。

**Agent Sandbox (v0.22.8)**: batch_docs + demo 的 system prompt 新增铁律——严禁探索宿主机（终端工具禁 whoami/uname/hostname/等）、严禁读取文件系统路径/环境变量/主机用户名，种子数据禁用可能泄露身份的信息（只用中性占位符如 张伟/李雪/王磊）。参见 [ADR-0056](../decisions/0056-data-isolation-audit.md)。

## 五、文档类型

| 文档 | 生成方式 | 内容风格 |
|------|----------|----------|
| req.md | batch_docs (1 次 LLM 调用 5 文档) | 需求分析, bullet points |
| arch.md | batch_docs | 架构方案, 或占位 |
| tasks.md | batch_docs | 任务拆分 |
| api.md | batch_docs | 接口定义, 或占位 |
| risk.md | batch_docs | 风险评估, RISK-XXXXXX 唯一编号 |
| demo HTML | demo agent (独立) | HTML 原型, 可交互, 多版本 |

所有文档生成通过 **MiniMax-M3** LLM。

### demo 版本管理 (v1.44 更新)

**版本写入流程** (`demo_version.write_demo_version`):
1. 读取现有 manifest → 确定下一版本号 vN
2. 写入 `demo_vN.html` + 更新 `demo_manifest.json` + 更新 `demo_latest.html` symlink
3. **内容检查** (v1.44): HTML < 3KB 且含"等待更多会议内容"/"暂无会议内容" → **拒绝写入**, 返回 `skipped: "placeholder"`
4. 成功 → 推送 SSE `demo-new-version` (version/summary/file_size/file) + 触发 proactive agent

**文件结构**:
```
docs/{meeting_id}/
├── demo_v1.html          # 版本 1
├── demo_v2.html          # 版本 2
├── demo_vN.html          # 最新版
├── demo_latest.html      # symlink → 最新版
└── demo_manifest.json    # [{version, created_at, trigger, summary, file_size, file}, ...]
```

## 六、数据流 (完整)

```
语音输入 (客户端麦克风)
  → PCM 帧 (16kHz mono int16)
  → WebSocket → 百炼 Fun-ASR-Realtime (云端, 实时逐句)
  → BailianCallback
     ├─ transcript JSON → WS 回客户端 (实时文字)
     └─ MeetingState.cleaned_text += 新句子 (每句追加)
  → on_state_changed 事件驱动 → task_manager.submit
     → should_skip_generation() 检查:
        ├─ finalized? → skip (会议已结束)
        └─ input_unchanged? → skip (hash 无变化)
     → batch_docs agent (fork 自 chat)
        → AIAgent.chat(prompt) → MiniMax-M3 → write_file × 5
     → demo agent (fork 自 chat)
        → AIAgent.chat(prompt) → MiniMax-M3 → write_file HTML
        → write_demo_version() (under publish lock + output hash dedup)
  → SSE doc-update / demo-new-version 事件
  → 客户端 6 文档面板 + Demo 预览更新
  → 每句新转写 → submit (task_manager 排队合并)
  → WS 断连 → finally 块也 submit
  → POST /close → _close_meeting → mark_finalized (持久化 .finalized) + 经验蒸馏 + 最终文档
```

**Chat 上传不入 KB (v0.23.1)**: `handle_chat_upload` 不再将文本/图片写入 Chroma KB，只落盘 `uploads/{mid}/`。agent 通过文件路径按需 `read_file`。图片上传后通过 vision API 分析，结果追加到 chat prompt。

**Prompt 纠正 (v0.23.1)**: 
- VP Chat system prompt: "6 个子 agent，你可以调度" → "2 个自动子 agent (batch_docs + demo)，系统自动调度，你只需专注回答"
- batch_docs.md: "材料已入 KB，搜索 KB 获取" → "已落盘 uploads/{mid}/，用 read_file 读取"

**Generation 去重与 Finalize 幂等 (v0.23.2)**: 
- **输入哈希去重**: `compute_input_hash()` 计算 sha256 规范化摘要（含 cleaned_text、5 类累积项、上传文件列表、最近 20 条 chat），`task_manager.submit` 提交前检查 `should_skip_generation()`：hash 与上次 completed generation 相同则跳过。
- **Finalize 持久化**: `mark_finalized()` 写磁盘 `.finalized` 文件，重启后仍有效。重复 stop 返回同一 finalization。
- **Idempotency key**: `{meeting_id}:docs:r{N}:{hash_prefix}`，无论触发来源（ASR/GKD/Chat/Close），同一 key 只产生一个 generation。
- **Demo 发布锁**: `write_demo_version` 内 `threading.Lock` per meeting，锁内 TOCTOU 二次去重 + 原子写（版本文件 + manifest + symlink）。
- **Generation 记录**: 持久化到 `data/meetings/generations/{id}.json`，含 input_hash、output_hash、status。

详见 [ADR-0058](../decisions/0058-generation-dedup-idempotency.md) · [Issue #44](https://github.com/zhangsheng377/vpbuddy/issues/44)。

per-meeting 单任务队列 + debounce + generation_id + global ThreadPoolExecutor(8)。
**v0.23.2**: `submit()` 入口前调用 `should_skip_generation()` (finalized / input_unchanged 检查)。

## 八、经验蒸馏 (experience)

**设计文档**: [ADR-0043](../decisions/0043-experience-distillation.md)

会议结束时从 MeetingState 自动提取 6 类经验候选，JSON 持久化 + 聚合索引。

**Experience 自排除 (v0.22.8)**: `search_experiences()` 新增 `exclude_meeting_id` 参数，batch_docs 调用时排除当前会议自身经验，防止循环自引用。chat 上传仅落盘不入 KB (v0.23.1)。

## 九、FastAPI 迁移 (v0.9)

**设计文档**: [ADR-0044](../decisions/0044-fastapi-migration.md)

`fastapi_app.py` 作为主应用，WebSocket 端点 + SSE 事件流 + REST CRUD。旧 `ui_server.py` 保留兼容。

**DELETE 资源清理完善 (v0.22.8)**: 删除会议时新增清理 uploads 目录、KB Chroma 记录、内存 agent cache (`_AGENT_CACHE`/`_CHAT_AGENT_CACHE`/`_CLEAN_AGENT_CACHE`)、experience 候选文件。
